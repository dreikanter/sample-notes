# Git workflow — rebase vs merge, when I use each

I've landed on a consistent practice after years of inconsistency. Writing it down to stop relitigating it.

**Rebase: for local, unpublished work**

When I'm working on a feature branch that hasn't been pushed (or that only I work on), I rebase onto main before merging. This gives a clean linear history.

```bash
git fetch origin
git rebase origin/main
```

If there are conflicts, I fix them commit by commit. The result is a branch whose commits sit neatly on top of main's latest.

**Merge: for shared or already-published branches**

If a branch has been pushed and other people have checked it out, rebasing rewrites history and causes problems for them. In this case, I merge instead.

```bash
git merge origin/main
```

This creates a merge commit but preserves the history everyone has.

**Squash merging for messy feature branches**

When a feature branch has 15 commits of "fix typo", "actually fix typo", "revert fix", I squash-merge it:

```bash
git merge --squash feature-branch
git commit -m "Add feature X (#123)"
```

One clean commit represents the entire feature. Useful for keeping main's history readable.

**Interactive rebase to clean up before PR**

Before opening a pull request, I often do:

```bash
git rebase -i HEAD~5
```

And squash or reword the last 5 commits. This is the most common reason I use rebase in practice.

Detailed guide: https://www.atlassian.com/git/tutorials/merging-vs-rebasing
