# Database transaction isolation levels — Kleppmann chapter 7 notes

Following through on the commitment from [[20250731_1876]]. Chapter 7 of DDIA on transactions [[20250703_1861]] is the most technically dense chapter I've read and also the most clarifying.

**The isolation levels (weakest to strongest)**

*Read Uncommitted*: reads can see data written by uncommitted transactions. Almost never what you want. Permits "dirty reads."

*Read Committed*: can only read committed data. Prevents dirty reads but allows "non-repeatable reads" — reading the same row twice in one transaction can give different results if another transaction committed between the two reads.

*Repeatable Read*: same row read twice in one transaction gives the same result. Prevents non-repeatable reads but may allow "phantom reads" — a query returning different rows if another transaction inserted/deleted rows matching the query predicate between the reads.

*Serializable*: transactions behave as if they ran one after another with no concurrency. Prevents all anomalies but is typically slower.

**The tricky part: what databases actually implement**

PostgreSQL calls its "Read Committed" and "Repeatable Read" by those names but the behavior differs slightly from the SQL standard. What Postgres calls "Repeatable Read" prevents phantom reads too (because of MVCC). What Postgres calls "Serializable" is Serializable Snapshot Isolation (SSI), which is an optimistic algorithm that's considerably less pessimistic than classic two-phase locking.

**My takeaway**

For most web application work, Read Committed (the default in Postgres) is appropriate. Upgrade to Repeatable Read or Serializable only when you've identified a specific anomaly you need to prevent.
