# Notes on the Temporal API — JavaScript date handling finally fixed

Spent a few hours with the Temporal polyfill, which was on my learning backlog [[20250531_1838]]. Here are the things that immediately made me understand why this replaces Date.

**What was wrong with Date**

`Date` represents a moment in time as milliseconds since the Unix epoch. This is fine for a low-level abstraction. The problem is that `Date` tries to also be a calendar date, a local time, and a UTC time simultaneously, and does all three badly.

`new Date(2025, 8, 6)` creates September 6, not August 6 — months are zero-indexed. `Date.getTimezoneOffset()` returns the local timezone offset in minutes, but it can change for DST and there's no way to ask about a specific timezone.

**What Temporal does instead**

Three distinct types for distinct use cases:

```javascript
// An exact moment in time (like Unix timestamp)
Temporal.Instant.from('2025-09-06T10:00:00Z')

// A calendar date with no time or timezone
Temporal.PlainDate.from('2025-09-06')

// A date with time but no timezone
Temporal.PlainDateTime.from('2025-09-06T10:00:00')

// A moment in a specific timezone
Temporal.ZonedDateTime.from('2025-09-06T10:00:00[Europe/London]')
```

**What this solves**

Duration arithmetic is now sane. In Temporal, `date.add({ months: 1 })` handles month-length differences correctly. In Date, you have to do this manually.

Timezone handling is explicit and correct. If you need "September 6 at 10am London time," you say that directly.

The polyfill is stable enough for production with a bundler.

Temporal proposal docs: https://tc39.es/proposal-temporal/docs/
