# HTTP caching — what the headers actually do

Always find myself checking these when setting up a new service. Compiled into one place.

**Cache-Control directives (the important ones)**

`max-age=N` — resource can be served from cache for N seconds without revalidation. Relative to when the response was received.

`s-maxage=N` — same as max-age but for shared caches (CDNs, proxies). Overrides max-age for those caches.

`no-cache` — does NOT mean "don't cache." It means "always revalidate with the origin before serving." The response can still be stored; it just needs a conditional request to confirm it's still fresh.

`no-store` — this one means "don't cache at all." Every request goes to the origin.

`private` — response is for a single user only; CDN must not cache it. Browser can cache it.

`public` — response can be cached anywhere, including by CDNs. Useful if you're adding this to responses that include authentication (counterintuitively — the resource itself is public even if access is controlled).

**ETags and Last-Modified for conditional requests**

When a cached response expires, the browser sends a conditional request:

```
If-None-Match: "v2-abc123"   (if server sent ETag)
If-Modified-Since: Mon, 20 May 2025 10:00:00 GMT   (if server sent Last-Modified)
```

If the resource hasn't changed, the server returns `304 Not Modified` with no body — very fast. The browser uses its cached copy.

**Practical strategy**

Static assets with content hashes in filenames: `Cache-Control: public, max-age=31536000, immutable`

HTML files: `Cache-Control: no-cache` (revalidate every time but still use cache if unchanged)

MDN reference: https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control
