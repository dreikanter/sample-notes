# SQLite for server-side use — what I learned

Following up on the backlog item [[20250531_1838]]. Spent a few evenings reading the SQLite documentation and a few articles on production use.

**The write concurrency situation**

SQLite uses file locking. By default, only one writer at a time. For a typical web app, this is more limiting than it sounds if you have many concurrent write requests — but WAL (Write-Ahead Logging) mode significantly improves the situation:

```sql
PRAGMA journal_mode=WAL;
```

In WAL mode, readers don't block writers and writers don't block readers. Multiple readers can proceed concurrently. There's still a single writer constraint, but for many read-heavy applications this is fine.

**Where it works well**

- Applications where reads vastly outnumber writes
- Single-server deployments (SQLite doesn't distribute across machines)
- Embedded applications, local-first apps
- Applications where data fits comfortably on one server

**Litestream for replication**

Litestream (https://litestream.io) replicates SQLite to S3 or similar storage. This gives you disaster recovery without the operational complexity of a Postgres replica. The latency for replication is typically under a second.

**The right mental model**

SQLite is not a "toy" database. Firefox uses it. WhatsApp used it. The question is not "is SQLite serious?" but "does this application's access pattern fit SQLite's constraints?" For a solo-developer SaaS app with modest write volume, the operational simplicity is a genuine advantage.
