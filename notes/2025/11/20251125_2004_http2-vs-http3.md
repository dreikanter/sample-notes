# HTTP/2 vs HTTP/3 — practical differences

Writing this up after a discussion about whether our API server should move to HTTP/3.

## HTTP/2 key features

**Multiplexing:** Multiple requests and responses over a single TCP connection, interleaved. Eliminates HTTP/1.1's head-of-line blocking at the HTTP layer.

**Header compression (HPACK):** HTTP headers are compressed, reducing overhead especially for APIs with many small requests.

**Server push:** Server can preemptively send resources. Rarely used well in practice.

**Binary framing:** HTTP/2 is binary, not text. More efficient to parse.

## The remaining problem with HTTP/2

TCP head-of-line blocking. If a TCP segment is lost, all HTTP/2 streams on that connection stall until retransmission succeeds. High packet loss environments hurt HTTP/2 disproportionately.

## HTTP/3 and QUIC

HTTP/3 runs over QUIC (Quick UDP Internet Connections) instead of TCP.

**QUIC solves TCP's head-of-line blocking:** Each stream is independent; a lost packet only affects the stream it belongs to.

**Faster connection establishment:** QUIC+TLS 1.3 can be 0-RTT (zero round trips) for subsequent connections to a known host, vs. TCP+TLS which requires multiple round trips.

**Connection migration:** QUIC connections survive IP changes (e.g., switching from WiFi to cellular) without reconnecting.

## Should you use HTTP/3?

For a server-side API in a datacenter with good network conditions: HTTP/2 is fine. HTTP/3 benefits are most pronounced in:
- Mobile clients with variable connectivity
- Global deployments with high latency paths
- High packet-loss environments

CDNs (Cloudflare, Fastly) support HTTP/3 on the client-facing side and can handle the termination for you.
