# Auth middleware refactor — design notes

Working with Elena on this. Writing up the design before we code.

## Current state

Authentication is handled in three different places:
1. A middleware function in `src/middleware/auth.ts`
2. A duplicate check inside the API gateway layer
3. A third check in a handful of route handlers that were written before the middleware existed

This means the auth logic has drifted — the middleware and the API gateway check now have slightly different token validation implementations. The route-level checks are the oldest and most wrong.

## Proposed approach

Single source of truth: `src/lib/auth/verifyToken.ts` with a well-tested, well-documented implementation.

All other auth points call this function rather than implementing their own verification.

```typescript
export async function verifyToken(token: string): Promise<AuthResult> {
  // 1. Check token format
  // 2. Verify signature
  // 3. Check expiry
  // 4. Check revocation list (Redis lookup)
  return { valid: boolean; userId: string; scopes: string[] };
}
```

The middleware becomes a thin wrapper:
```typescript
export const authMiddleware = async (req, res, next) => {
  const token = extractBearerToken(req.headers.authorization);
  if (!token) return res.status(401).json({ error: 'Missing token' });

  const result = await verifyToken(token);
  if (!result.valid) return res.status(401).json({ error: 'Invalid token' });

  req.auth = result;
  next();
};
```

## What we're removing

The API gateway check is redundant if the middleware runs on all routes — removing it simplifies the gateway config. The route-level checks are all going away.

## Testing plan

- Unit tests for `verifyToken` covering all validation branches
- Integration test that verifies the middleware correctly rejects expired and malformed tokens
- Regression test against the three routes that had their own checks
