# React Server Components — mental model notes

Finally taking the time to properly understand RSC after months of it being in the background of Next.js work. Writing this to solidify my understanding.

Reference: https://react.dev/blog/2023/03/22/react-labs-what-we-have-been-working-on-march-2023

## The core distinction

**Server Components** render on the server. Their output is sent to the client as a serialized tree, not HTML. They can access databases and filesystems directly. They cannot use state, effects, or event handlers. They are the default in Next.js 13+ App Router.

**Client Components** are the traditional model: rendered on the client (with optional SSR/SSG for initial HTML). They use `'use client'` directive at the top. They can use state and effects.

## What this changes

Previously: data fetching happened either at the page level (getServerSideProps, getStaticProps) or in client components with useEffect+fetch. RSC lets data fetching happen anywhere in the component tree, co-located with the components that need it, without client-side waterfalls.

A deep nested component can fetch its own data from the database without that fetch chain happening in the browser.

## Composition rules

- Server components can render client components
- Client components cannot render server components (except by passing them as children props)
- This means you push the `'use client'` boundary down as far as possible — keep large, data-heavy components as server components

## When I reach for client components

- Any user interaction (onClick, onChange, etc.)
- Browser APIs (localStorage, navigator, etc.)
- Custom hooks that depend on state or effects
- Third-party libraries that aren't RSC-aware
