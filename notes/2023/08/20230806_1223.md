# Meeting notes — API rate-limit post-mortem

Date: 2023-08-06  
Attendees: me, Elena, Marcus (infra), Priya (product)

## What happened

On July 31st between 14:00 and 16:30 UTC, the search API returned 429s to roughly 12% of requests. This affected the mobile client most visibly because it has a shorter retry timeout than the web client. Users saw search fail silently.

## Root cause

The upstream search provider tightened their burst limit policy without announcing it in the changelog. Our retry logic was using exponential backoff starting at 500ms, which was within the old limit but caused us to cluster retries in a way that consistently hit the new 60-requests-per-10-seconds ceiling.

## Actions

1. Marcus will implement jitter on the backoff — randomizing within ±30% of the calculated delay. Classic technique, documented here: https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/
2. Elena will add a circuit breaker so that if error rate exceeds 5% over 30 seconds, we stop hammering and surface a graceful error message.
3. I'll write a runbook for the on-call rotation covering how to identify provider-side vs. client-side 429 patterns.
4. Priya will request a written SLA and changelog commitment from the search vendor.

## What went well

Alerting fired within 3 minutes of threshold crossing. The on-call engineer had context fast.

## What was slow

The communication to users — the mobile error message just said "search unavailable" with no retry guidance. Fixing this is now a P1 for the client team.

Next post-mortem review in 2 weeks.
