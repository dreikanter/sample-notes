# Git rebase workflow — notes for the team

Following last sprint's merge conflict mess, writing this up for the team wiki. Posting here first to workshop the language.

## The problem with pure merge workflows

When everyone's merging feature branches directly into main, the history becomes a tangle of merge commits that makes `git bisect` unreliable and `git log --oneline` hard to read. We had a bug last week that took 40 minutes to bisect because the history wasn't linear.

## Proposed: rebase before merge

1. Start feature branch from latest main.
2. Do your work.
3. Before opening PR, `git fetch origin && git rebase origin/main`.
4. Resolve conflicts on your branch — you own your changes.
5. Force-push to your feature branch (it's yours, this is fine).
6. Merge into main via PR with a standard merge commit (or squash, depending on branch size).

## Key points

- Rebase doesn't change the content of commits, only their parent. The diff is identical.
- Never rebase shared branches. Only rebase your own feature branches.
- If you're in the middle of a rebase and things go wrong: `git rebase --abort`.
- Interactive rebase to clean up history before PR: `git rebase -i origin/main`. Squash fixup commits, rename confusing messages.

## Resources

- Pro Git chapter on rebasing: https://git-scm.com/book/en/v2/Git-Branching-Rebasing
- Atlassian's comparison of merge vs. rebase: https://www.atlassian.com/git/tutorials/merging-vs-rebasing

The most common objection is "rebase rewrites history." It does, but only on branches that haven't been shared. The point is to clean up before sharing.
