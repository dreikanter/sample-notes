# Debugging a memory leak — notes from this week

Spent two days tracking down a memory leak in the Node.js API service. Writing it up while it's fresh.

## Symptoms

Heap usage grew steadily from ~180MB at startup to >1GB over about 6 hours before the process was restarted by the health check. No obvious pattern to when it was fastest.

## Tools used

Node's built-in `--inspect` flag plus Chrome DevTools' Memory tab: https://nodejs.org/en/docs/guides/debugging-getting-started

Took heap snapshots at startup, 1 hour, 3 hours. Compared the Snapshot Comparison view to find objects growing.

## What I found

A `Map` used as a cache in the search suggestions service was growing without bound. The cache was keyed by search query string and eviction was supposed to happen based on a 10-minute TTL. The bug: the eviction interval was set up inside an async function that wasn't being awaited properly, meaning the `setInterval` was being called on every request instead of once at startup. Each interval ran every 10 minutes and cleared the cache — but there were now hundreds of intervals all firing at slightly different times, none of them cleaning up after themselves, and each one holding a closure reference to the cache object.

The cache entries themselves were small. The held closures were the leak.

## Fix

Moved the interval initialization to module scope (runs once on import), verified with a small test that only one interval is active.

## What I'd do differently

Add heap metrics to the Prometheus dashboard [[20230922_1272]] immediately rather than waiting for a symptom. A gradual, steady growth curve is a leak signature; a dashboard would have caught it at 200MB instead of 1GB.
