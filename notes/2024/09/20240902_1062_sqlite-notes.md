# SQLite — practical notes for local-first projects

SQLite is the right choice far more often than it gets credit for. These are patterns I've found useful across a few small projects.

## WAL mode

Default journal mode is DELETE, which is fine for single-writer use. For anything with concurrent reads (e.g., a server process and a CLI tool both hitting the same file), enable Write-Ahead Logging:

```sql
PRAGMA journal_mode=WAL;
```

This persists across connections. WAL allows one writer and multiple simultaneous readers without blocking. The trade-off: you get a `-wal` and `-shm` file alongside your database while WAL is active.

## Useful PRAGMAs at connection open

```sql
PRAGMA foreign_keys = ON;     -- not enabled by default
PRAGMA synchronous = NORMAL;  -- safe with WAL, faster than FULL
PRAGMA cache_size = -64000;   -- 64 MB page cache (negative = kibibytes)
PRAGMA temp_store = MEMORY;
```

## JSON columns

SQLite has had JSON functions since 3.38. Storing structured data in a TEXT column and querying with `json_extract()` works better than it sounds:

```sql
SELECT json_extract(metadata, '$.author') FROM notes WHERE id = 1;
```

Not a replacement for proper normalisation, but useful for optional fields and prototype schemas.

## FTS5 full-text search

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(title, body, content=notes, content_rowid=id);
```

Trigger maintenance is needed to keep the FTS index in sync with the base table. The [FTS5 documentation](https://www.sqlite.org/fts5.html) covers this clearly.

## Backup one-liner

```bash
sqlite3 mydb.sqlite ".backup mydb_backup.sqlite"
```

The `.backup` command is safe to run against a live database.

Official docs: [sqlite.org](https://www.sqlite.org/docs.html)
