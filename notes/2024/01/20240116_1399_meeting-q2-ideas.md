# Q2 early ideas — brainstorm

Not a plan, just things that came up in conversation and I don't want to lose.

## From the offsite conversation (see [[20240207_1368]])

Devlin raised the idea of adding feature flags to the event pipeline so we could route specific event types to different processing queues. This would let us experiment with processing latency for less critical events without affecting the core flow. Worth spec-ing.

Marcus wants to explore ClickHouse for the reporting layer instead of the Postgres read replica long-term. His argument: ClickHouse is purpose-built for aggregations over time-series data and would change the query times from 80ms (current with indexes) to something under 10ms at any scale. The operational complexity is higher but so is the ceiling.

I want to prioritize the observability gap — specifically adding distributed traces to the main request path. The runbook (see [[20240302_1380]]) makes the gap obvious: I can describe failure modes but I can't efficiently diagnose them in real time.

## From product

The product team wants a "real-time" dashboard for the customers. They mean within 60 seconds, not true real-time. This is achievable with the current architecture but requires a new API endpoint and some careful cache design.

## What I think matters most

Observability first — it makes everything else easier to build and debug. Then the feature flags, which unlock experimentation. The ClickHouse conversation is real but probably Q3 after we've understood the replica's limits.

Reference: [Feature Flags, by Martin Fowler](https://martinfowler.com/articles/feature-toggles.html) for the implementation patterns we'd follow.
